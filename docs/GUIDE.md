# Foxy guide

The feature-by-feature reference for the dashboard, the exports and the agent tools. For installing and running Foxy, see the [README](../README.md).

**Contents:** Views and output (Timeline, Call site, Code owners, Sorting, Columns, Endpoints, Audit a phase, Identical requests, Filters, Markers and phases, Guide, Time format, Launched from, Package links, Source link, Big captures, Play and pause, GitHub links, Logo, Menu and shortcuts, Highlights, Log storage, Desktop menus, Exports) · Agent access (MCP) · Limits · Tests.

## Views / output

- **Timeline**: every request in order. The **Call site** column leads with the `method()` that called `fetch`. Beneath it is what called that method (`↳ useThing()`): the nearest app frame (the hook or component), else the next `@metamask` method by a different name. When the stack ends at the call site, which Hermes stacks usually do after an `await`, the file tail is shown instead and nothing is guessed. The caller is in the app color when it is app code (blue) and the controller color for an `@metamask` method (lime). Click a row for the full call chain (oldest caller first, wrapper frames collapsed) plus the request and response (query params, headers, body).
- **Code owners**: team chips come from CODEOWNERS for the file that made the call (`.github/CODEOWNERS` for `app/`, the core monorepo's for `@metamask/<pkg>`; set `FOXY_REPO` / `FOXY_CORE` if the paths differ). Third-party calls show the package name instead (for example `@segment/analytics-react-native`), plus dashed *via* chips for the team that owns the caller. The **caller** (the `↳` line under Call site) counts too: when it belongs to a different team than the call site, that team gets a dashed *via* chip next to the call site's, so a hook owned by one team that goes through a controller owned by another shows both. Filtering by either team matches the request, the Endpoints table and the audit export list both, and the call chain marks the same frame as *started from*. `@metamask/*` packages with no CODEOWNERS entry show a dashed fox chip, and unmatched app files show `unowned`.
- **Sorting**: click a column header to sort by it (again for the other direction, a third time to go back to the default order). The Timeline always keeps its marker phases: ID and Time choose which end comes first, and any other column orders the requests inside each phase (phases stay newest first). Duration and count columns (Duration, Calls, Identical Dupes, Avg Duration) sort largest first. Rows with no value always sit last.
- **Columns**: drag a header label to reorder, drag a header edge to resize (or focus it and use the arrow keys), double-click an edge to reset that column, **Reset columns** restores the defaults. Layout is saved in the browser.
- **Endpoints**: grouped by `METHOD host/path` with call counts, *identical duplicate* counts, status mix, average latency, an activity lane (every call as a tick on the capture timeline; ringed ticks repeat an earlier identical request), call sites. Click a row for the full breakdown:
  - summary cards (calls, identical dupes with redundant ms/bytes, latency p95/max, burst size, first and last time, payload);
  - every call on a rail with when it happened (relative and wall-clock), the gap since the previous call (`⚡ same time` for bursts), status, size, call site and owner, with repeats flagged (`same as #N`); click a call to open it in the Timeline;
  - which query params change between calls and which stay the same, and who calls the endpoint;
- **Audit a phase** (Endpoints tab): focus a phase (its focus icon, or its row in the Markers panel), then turn on **Audit** beside the phase pill. Only then does the table get a **Verdict** column, and each endpoint's detail a **Verdict** panel with Keep / Defer / Move / Drop and a reason. The **?** beside the Verdict title opens a small legend of what the four mean. Endpoints without a verdict read "no verdict" and stay listed. Verdicts are kept per phase, in the browser (`foxy.audit.v1`), keyed by the marker's label, so the same endpoint can be Keep in one flow and Defer in another. They are included in the markdown and CSV exports.
  - Audit is a switch at the trailing edge of the filter row; turning it on or off animates the Verdict column, the panel and the Export button in and out. While it is on, an **Export Audit** button appears beside it and opens the same export dialog as every other download button (see **Exports**), scoped to the phase.
- **Identical** means the same method and URL. For POST/PUT/PATCH/DELETE the body must match too (size plus a hash of the captured preview); with no body information a non-GET request is never called identical, so JSON-RPC and analytics batches are not falsely flagged. Turn on `FOXY_BODIES` for the strongest check.
- **Filters**: ownership buttons (We own / Third-party / Unowned) with counts, plus Failed, Duplicates and Highlighted toggles. The search box at the top does the same for host, path, call site and team: while it has text the field is tinted orange and shows how many requests it keeps (`3 of 32`); Esc clears it, and clicking anywhere outside lets go of the box without clearing the search. When nothing matches it turns red and the table offers a Clear search button. **Highlight** a request with the highlighter icon in its open row (or `H`); highlighted rows get a MetaMask-orange tint, with orange dividers, and the **Highlighted** toggle (also a quick filter in the Filters panel) shows only those. Highlights survive a dashboard reload and are removed by Clear. Clicking a team, package or status pill (in a row or its detail) filters by it; click it again to clear. A status pill filters by its kind (2xx, 4xx, Failed…) through the Filters panel.
- **Markers & phases**: a marker is a flag you drop while using the app; everything captured after it belongs to that phase until the next marker.
  - **App relaunches**: a Metro reload, a crash, a relaunch or a fresh install gives the app a new session, and it joins the capture on screen: markers stay, the clock keeps its time zero and request numbers carry on from the last one. The dashboard says so with a short notice. Press **Clear** before a fresh install to start a capture from zero.
  - **Add**: press `M` or click **Markers**, type a label and press Enter, or tap a quick-add chip (your own labels are remembered). The *Now / 5s ago / 30s ago…* dropdown backdates a marker you noticed late.
  - **See**: each phase gets a colour. The activity strip shades the phases and labels their flags (click a flag on the Timeline to jump to that phase; on Endpoints it focuses that phase instead, and clicking it again shows every phase, without leaving Endpoints), the waterfall draws a line per marker, and the Timeline gets a collapsible header per phase with its time range, ownership mix, requests, new endpoints, identical dupes and failures (`🌙 quiet` when nothing was requested).
  - **Zoom**: **Only this** on a header (or the target icon in the panel) filters Timeline and Endpoints to that phase; Endpoints also has a Phase column showing where each endpoint first appeared.
  - **Edit**: rename a marker in the panel, delete it with the bin (neighbouring phases merge).
  - **End a phase**: the stop icon on the last phase (in its header, or in the Markers panel) closes it where you are, so a flow you are done with stops collecting. Everything after that moment, until the next marker, is **Between phases**, so idle traffic does not count toward the flow. Reopen with the icon that replaces it. Ending is one-way until reopened (a second End keeps the first time), and only the latest marker can be ended or reopened: an older phase is already closed by the marker after it, and reopening it would swallow the phases in between and scramble their order (the UI hides the icon on older phases and the server answers 409). `POST /api/marker/<id>/end` and `DELETE` (reopen).
  - **Export a phase**: the download icon on a phase header (or on its row in the Markers panel) opens the export dialog for that phase. Its *JSON, full detail* option saves every request of the phase in full: headers, bodies, the call chain with owners and GitHub links, plus the phase's totals. The last marker's phase is still collecting, so it saves what has arrived so far (`phase.open` is `true` and the file is named `…-so-far.json`); download it again later for more. The file is cut on the server, so Pause and the filters do not change it. Scripts can use `GET /api/export/phase?marker=<id>` (`marker=pre` for before the first marker, `&format=md` for the markdown table).
  - **Export**: see **Exports** below. Agents can add, list and end markers and export phases with the MCP tools (see **Agent access (MCP)** below).
  - **One time axis**: the activity strip, the Waterfall column and the Endpoints call lanes all share it, so a bar means the same moment everywhere. It is drawn to scale, except that a long stretch with no request running (more than 15s, or 5% of the capture) is shortened to a hatched break labelled `⋯ 1h 12m`, so a launch followed by an hour of idling and then a burst of activity does not squash the burst into a sliver. It only does this when it frees up at least a quarter of the width, so ordinary captures stay exactly to scale. Time labels always show real capture time. Filtering to one phase (**Only This**) zooms the axis to that phase.
  - Marker labels on the strip never overlap and never run off the window: they stack in up to three rows, flip to the left of their line near the right edge, and a marker with no room left keeps its line and shows as a dot (hover for its name).
  - Identical dupes are counted against the whole capture, so a repeat in a later phase of something fetched earlier is flagged.
- **Guide**: it opens on every launch until you tick *Don't show this guide when Foxy opens*; the `?` button (or the key) reopens it. It has illustrated topics (Start here, Markers & phases, Reading the Timeline, Endpoints & verdicts, Filters & duplicates, Shortcuts). To document another view, add an entry to the `HELP` array in `dashboard/js/18-guide.js`; illustrations live in the `ART` object in `dashboard/js/17-guide-art.js` and are plain monospace strings with colour spans.
- **Time format**: the menu switches every time shown in the dashboard between `1m 23.4s`, `01:23.40` and plain seconds (`83.40s`). The choice is remembered; copied markdown always uses plain seconds.
- **Date and time**: besides the relative **Time** (`+1m 23.4s` into the capture) and **Duration**, the Timeline has a **Started at** wall-clock column (`15:08:06.421`, local time) and Endpoints a **First call at**; hover either for the full date, weekday and time zone (Endpoints also shows the last call). A request's detail shows the date, when it started and when it finished. Exports carry the same moments as local ISO 8601 with the UTC offset (`2026-11-25T15:08:06.421-05:00`).
- **Columns**: number-like columns (ID, Time, Method, Status, Duration, and Calls / Avg Duration / First in Endpoints) size themselves to the widest value in the capture, within a realistic range, so digits never clip as the numbers grow. The other columns share the remaining width and can be dragged to resize.
- **Default column order** follows Charles, Proxyman and Chrome DevTools: what the request is and how it ended, then who made it, then when. Timeline is ID, Method, Status, Host, Path, Call site, Launched from, Code owners, Started at, Time, Duration, Waterfall. Endpoints is Endpoint, Statuses, Calls, Identical dupes, Avg Duration, Call sites, Code owners, Phase, First call at, First, Activity (plus Verdict while auditing). Saved layouts from older versions are ignored once so you get this order; **Reset columns** restores it any time.
- **Launched from view**: every request records the screen the app was showing when it was made. The Timeline's **Launched from** column shows it at a glance: the screen name, the navigators just above it, and an `on mount` flag when the request fired as the screen appeared (sortable by screen; a build that does not report it reads "(not reported)"). Open a request and the strip at the top of its detail names the screen, the navigator path to it (`Main › SwapsAmountView`), how long the screen had been showing (a request fired within half a second of a screen opening is flagged, since it is most likely triggered by mounting it), the app state when it is not in the foreground, and the screen's param *names* (never values). Requests made before the navigator mounted read "Before navigation was ready". The Filters panel has a **Screen** section, and the filter box matches screen names. The app side lives in `app/dev-tools/Foxy/FoxyView.ts` and is registered from `NavigationService` only when `FOXY="true"`. Rebuild the app once to start sending it; older captures show "Not reported".
  - **Package links**: call-chain frames from `node_modules` link to the package's source on GitHub. MetaMask packages (`@metamask/*`) link to the release tag in `MetaMask/core` at the line behind the published `dist` file, using its source map (for example `src/api/base-client.ts:194`). Packages from other repos link to the file and line at their release tag (`v<version>` or `<name>@<version>`, read with `git ls-remote` the first time a repo is needed) when they ship a source map. Anything else links to the release folder or the repository front page, and frames with no repository stay plain text. This is in `packages.mjs`.
  - **Source link**: the strip also shows where the screen is defined, as `file:line`, linked to that line on GitHub (the same `FOXY_GITHUB_*` settings as call-site links apply). Foxy works this out on the server by reading the `<Stack.Screen name component>` tags in `app/` (`views.mjs`), following imports, `#app/*` aliases and re-exports to the component's declaration, and shows a "Registered in" link when the navigator that mounts it is somewhere else. It is static analysis re-run at most every 15s, so lines follow your edits. Config-driven screens are read too: a `{ key, name }` object (such as a bottom tab definition) is joined to a `{ key: Component }` map on the same key, and a navigator that is itself a screen (`initialRouteName`) is followed to the screen it opens first. Screens none of these reach fall back to a file named after the route, labelled "Best match", and otherwise show no link.
- **Big captures**: the Timeline and Endpoints lists are virtualized, so only the rows near the viewport exist in the page (about 50, however long the capture). Scrolling, filtering and jumping to a request, phase or strip bar stay fast with tens of thousands of requests, and the view stays put when new requests arrive while you are scrolled down the list.
- **Play / pause**: the round button in the header freezes the view while Foxy keeps recording. A badge counts the requests being held. Press play and they appear, with a divider in the Timeline (when you paused, for how long, and how many requests arrived while paused) so you can tell them from what was already on screen.
- **Filters**: the button at the right of the filter row (or `F`) opens a panel styled like Markers. Pick several code owners, statuses, methods or hosts (any of them matches), flip a section to "Is not" to exclude instead, match owners on the call site, the code that started it, or either, and set a minimum duration. Every team in the app's and core's CODEOWNERS is listed (with a count of 0 until it makes a request), so you can star yours before capturing anything, and the **My teams** quick filter shows only their requests (stored in the browser). Active filters appear as removable pills.
- **GitHub links**: in a request's call chain, the file path of every app and project frame opens that file at that line on GitHub (`#L<line>`, GitHub cannot highlight a column). Packages and `@metamask/*` frames stay plain text because their frames point at built `dist` files, not source. Foxy links to your `origin` repo at `HEAD` when it is on a remote branch, otherwise at the merge-base with `origin/main`, so the lines match the running code. Set `FOXY_GITHUB_REPO=owner/name` and `FOXY_GITHUB_REF=<branch|sha>` to override (for example once your branch is pushed). Unpushed local edits can shift line numbers.
- **Logo**: the header and guide use the animated MetaMask fox (`vendor/foxy-loading.riv`, played with the vendored Rive web runtime). It loops forever while the feed is live; when you pause, he stops and faces straight ahead (a second, never-played copy of the artboard, because the loop cannot be scrubbed to that pose), and he starts looking around again on play. People who prefer reduced motion get the still fox all the time, and falls back to the 🦊 emoji if the files are missing. 
- **Menu**: the hamburger holds the Theme picker (Dark, Light, Navy, Orange; saved in the browser), Time format, Reset columns, Export…, **Clear Highlights** (enabled only while something is highlighted), **Log Storage** with **Clear Log File**, and Clear (a fresh capture: request IDs start again at 1 and the clock at +0s from that moment; markers and highlights go too). Durations show their unit (`212 ms`, then `1.24 s` from a second up). Keyboard: `1` and `2` switch between Timeline and Endpoints, `/` focuses the filter, `M` opens markers, `E` stops the running phase (press it again to resume it) and `P` pauses or resumes live updates and `H` highlights the open request. `Esc` closes whatever panel is open first; with nothing open it folds the row you opened in the current tab. The shortcuts are ignored while you type in a field.
- **Exports**: every download button (a phase header, a phase row in the Markers panel, the divider between phases, **Export Audit**, and **Export…** in the hamburger menu) opens one dialog. Pick a format, then tap the button at the bottom (it reads *Download JSON*, *Download CSV* or *Copy Markdown* to match; its width never changes, so nothing jumps). The format you pick is remembered for next time. The title shows what is being exported. A download closes the dialog; a **copy** leaves it open and shows *Copied!* for a moment, so you can copy again or pick another format.
  - **Every export says where it came from.** JSON files carry a `foxy` block (or `exportedBy` in the agent JSON); CSV files open with `# ` comment lines; markdown opens with a quote block. All hold: *Exported from Foxy* with its version and link, when it was exported (local ISO time and time zone), the scope (whole capture, a phase or filtered, with request counts), when the capture started, the app (platform, OS version, device, MetaMask Mobile version and build, environment such as `dev`, build type), the **source checkout** (branch, commit, uncommitted changes), the GitHub repo and ref call-site links use, Metro, and the machine. The app details come from the bridge's `hello`, so they appear once the app is on a build that sends them; older builds simply omit those lines. Scripts can get the CSV or markdown block from `GET /api/export/header?format=csv|md&scope=…&shown=…&total=…`, and `GET /api/status` has the same facts under `environment`.
  - **JSON, full detail**: for a phase, every request in full (headers, bodies, call chain with owners and GitHub links) plus the phase totals; for the whole capture, `foxy-capture-<time>.json` with `foxy` (export time, session, platform, build), `summary`, `markers`, `phases` and `requests` in time order. Both ignore filters and Pause. Scripts: `GET /api/export/phase?marker=<id>` and `GET /api/export/capture` (`?session=<id>`, 404 for an unknown one).
  - **CSV, one row per request** (ID, time, started at, phase, method, host, path, query, status, error, duration, finished at, size, identical dupe, code owners, via caller, screen, call site, started from) and **CSV, one row per endpoint** (phase, endpoint, calls, identical dupes, failed, statuses, avg and p95 ms, bytes, first call, first and last call at, owners, call site, verdict, reason). Times are local ISO 8601. The comment lines at the top are one cell each (no commas), so a spreadsheet keeps them tidy; to load the file with pandas use `comment='#'`. UTF-8 with a BOM so Excel reads it; any text that starts with `=`, `+`, `-` or `@` is prefixed with `'` so a spreadsheet never runs it as a formula.
  - **Markdown table, copy** and **Markdown file**: the same table, copied or saved as `foxy-<scope>-<audit|endpoints>-<time>.md`. For a phase it is the audit table (phase window, counts by verdict, a row per endpoint with verdict and reason); for the whole capture it is the phases table plus the Endpoints table. Also `GET /api/export`.
  - **JSON for an agent** (phases only): the verdicts, reasons and call sites with instructions an AI agent can act on (`foxy-audit-<phase>.json`).
  - For the whole capture, when filters are active a checkbox offers to export only what they show (CSV and Markdown; the full JSON always has everything).
- Raw log: `logs/foxy.jsonl` in the data folder (the app) or the Foxy folder (from source); `FOXY_LOG_FILE` overrides it. It only grows, and is only used by `replay.mjs`. The dashboard menu's **Log Storage** shows its size and path and **Clear Log File** empties it (`GET /api/storage`, `POST /api/storage/clear`); the audit verdicts next to it and the capture on screen are left alone. It lives in the dashboard menu only, so it works the same in the app, a browser tab and `yarn foxy`.
- **Desktop menus**: there are two on purpose, and no preferences window. The dashboard has to work in a browser tab and under `yarn foxy`, where there is no native menu, so everything about the capture and the view (theme, time format, columns, export, highlights, log storage, clear) lives in the in-app menu. The macOS menu bar holds only what needs the operating system: **File > Switch MetaMask Mobile Folder…** (`⌘O`, with **Recent Folders**, **Show Folder in Finder** and **Set Up App for Foxy…**), and **Foxy > Open Dashboard in Browser**, **Show Data Folder** and **Copy MCP Config…**. The folder switcher is also shown at the top of the in-app menu when it runs inside the app (through `desktop/preload.cjs`, which exposes only `folder()` and `switchFolder()`). Foxy restarts to switch folders and asks first when that would discard a capture; if another Foxy is serving the window, the choice is remembered for the next launch.
- Replay an old capture into a running dashboard (no app needed): `node replay.mjs [logfile] [port]`.

## Agent access (MCP)

The app can copy a ready config: **Foxy > Copy MCP Config…**. It runs `mcp.mjs` through the Foxy binary itself, so nothing else has to be installed:

```bash
claude mcp add foxy -e ELECTRON_RUN_AS_NODE=1 -- /Applications/Foxy.app/Contents/MacOS/Foxy /Applications/Foxy.app/Contents/Resources/app/mcp.mjs
```

From source: `claude mcp add foxy -- node /path/to/foxy/mcp.mjs`. The MCP server talks to a running Foxy on `FOXY_PORT` (default 8098).

Tools:

| Tool | What it does |
|---|---|
| `network_list`, `network_get`, `network_summary`, `network_export_markdown` | Read the capture: requests, one request with its call stack, endpoints grouped, the markdown skeleton |
| `marker_add` | Drop a marker (`label`, optional `agoSeconds`). It starts a phase and closes the previous one |
| `marker_list` | The session's phases: id, label, start and end, `open`/`ended`, totals (requests, new endpoints, identical dupes, failed, bytes) and how many endpoints have a verdict |
| `marker_end` | End the newest marker's phase now (anything after it, until the next marker, is "Between phases"); `reopen: true` undoes it. Older markers answer with an error, as in the dashboard |
| `network_export_phase` | Everything one phase holds. `phase` is a marker id or label (or `pre`; part of a label works when only one phase has it; omit for the newest). `format: "json"` (default) writes the full records to a file and returns its path with the phase totals; `format: "md"` returns the markdown table inline. The newest phase is still collecting, so it reports `open: true` |
| `network_export_capture` | The whole session as a file (path, request/marker/phase counts, the phases) |
| `audit_get` | A person's audit of one phase: what the verdicts mean, then every endpoint the phase called with its verdict (`keep`, `defer`, `move`, `drop`, or `null` when unjudged), their reason, calls, identical dupes, statuses, owners and the call sites (function, file, line) to change. `phase` as in `network_export_phase`; `verdict` narrows it (`defer`, `judged`, `unjudged`…). The same document as the dashboard's *JSON for an agent* export. Small ones come back inline; a big one is written to a file |
| `network_clear`, `status` | Clear the capture; server status |

Big exports go to a file, not into the agent's context: `$TMPDIR/foxy/` by default, or `FOXY_EXPORT_DIR`. The file is named like the dashboard's download (for example `foxy-onboarding-visible.json`). A scripted run looks like: `marker_add` "Onboarding visible", drive the app, `marker_add` "Done" (which closes the previous phase), then `network_export_phase` with `phase: "Onboarding visible"`. If a phase name does not match, the error lists the phases that exist. Verdicts are given in the dashboard and synced to the server (kept in `logs/audit.json`, or `FOXY_AUDIT_FILE`, across restarts), so `audit_get` can read them.

## Limits

- Only JS-initiated requests are seen. Native-side prefetches (registered in `MainApplication.kt` / `AppDelegate.swift` before JS boots) are not.
- Stacks are the synchronous call stack at `fetch()` time; after an `await` you see the polling function, not the original trigger.
- Header names are recorded, but values for credential-like headers (authorization, cookie, api keys, tokens) are replaced with `[redacted]`.
- Request and response bodies are **off by default**. Set `FOXY_BODIES="true"` in `.js.env` to record capped previews. They can contain tokens or personal data, so use this only on throwaway wallets.

## Tests

`npm test` (the two tests that read real CODEOWNERS files are skipped unless `FOXY_REPO` and `FOXY_CORE` point at a MetaMask Mobile and a MetaMask core checkout). `npm run smoke` starts the desktop shell headless and checks the dashboard answers. The in-app bridge has its own Jest tests in the MetaMask Mobile repo: `yarn jest app/dev-tools/Foxy`.

## Where the dashboard code lives

`dashboard/index.html` is the markup, `dashboard/styles.css` the styles and themes, and `dashboard/js/` the behaviour, one file per area: `01-state.js` (the capture, filters and sorting), `02-history.js` (Back and Forward), `03-live.js` (connection and Pause), `04-format.js` (time display and the shared time axis), `05-chips.js` (owner chips and call-site cells), `06-filtering.js`, `07-phases.js`, `08-grid.js` (columns), `09-verdicts.js`, `10-detail.js`, `11-virtual-list.js`, `12-rows.js`, `13-export.js`, `14-render.js`, `15-interactions.js`, `16-menu.js` (menu and shortcuts), `17-guide-art.js` and `18-guide.js`, `19-markers-panel.js`, `20-filters-panel.js`, `21-main.js` (the WebSocket and start-up) and `22-logo.js`.

The server joins them into one page on every request: the stylesheet becomes one `<style>` and the scripts, in file-name order, one `<script>`. They share one scope on purpose, so any file can call a function from any other, and a reload shows an edit. To add a file, give it the number of where it belongs. Code that runs while the page loads (rather than in a function) can only use `const` and `let` values from files before it.
